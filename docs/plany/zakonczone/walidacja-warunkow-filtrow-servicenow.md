# Walidacja zmiennych katalogowych i złożonych warunków filtrów ServiceNow

**Status — wdrożony w źródłach i odebrany na zwykłym koncie ADEO.** Po każdej sprawdzonej serii zmian zaznacz wykonane kroki i zapisz wynik. Etap zamknij po wykonaniu jego kroków. Przy przerwaniu zapisz stan i najbliższą czynność.

## Cel i stan wyjściowy

Aplikacja ma rozpoznawać poprawne warunki takie jak data startu w formularzu wniosku i pozwalać zmieniać ich wartości bez dodawania wyjątków do kodu. Ustalone zapytanie nadal przechodzi do Table API w całości. Codzienna aktualizacja ze sprawdzoną definicją wykonuje jedno żądanie po rekordy bez otwierania klasycznej listy. [Kontrakt odczytu list](../../kontrakty/kontrakt-odczytu-list.md) · [Decyzja 037](../../decyzje/037-definicje-filtrow-bez-dom.md)

Przed wdrożeniem `filter_metadata.py` rozpoznawał warunki z adresu, sprawdzał zwykłe pola i odwołania w metadanych tabel oraz zapisywał definicję filtra. Dla SCTASK dopuszczał dokładny warunek daty startu pochodzący z konfiguracji kafelka **Wnioski Smartfon**. Zapisany adres filtra **Wnioski** przeszedł lokalną walidację po poprawce. Pełny odczyt w ADEO potwierdzono podczas odbioru tej migracji. [Walidacja w źródłach](../../../neto_incident_monitor/filter_metadata.py) · [Definicja kafelka](../../../neto_incident_monitor/analytics_config.py)

Dokumentacja ServiceNow opisuje zmienne katalogowe dla SCTASK i RITM w raportach oraz listę zmiennych w odpowiedzi po odczycie pozycji katalogowej. Dostęp zwykłego konta i działanie warunków w Table API trzeba sprawdzić w ADEO. Table API może pominąć nieprawidłowy fragment zapytania i zwrócić rekordy, więc HTTP 200 i zgodna liczebność odpowiedzi nie dowodzą, że serwer zastosował wszystkie warunki. [Zmienne katalogowe w raportach](https://www.servicenow.com/docs/r/now-intelligence/reporting/use-service-catalog-variables-in-report.html) · [Service Catalog API](https://www.servicenow.com/docs/r/api-reference/rest-apis/c_ServiceCatalogAPI.html) · [Table API](https://www.servicenow.com/docs/r/api-reference/rest-apis/c_TableAPI.html)

- [x] **Etap 2. Potwierdzenie zmiennych i działania operatorów w ADEO**
  - [x] Sprawdź odczyt definicji po dokładnym identyfikatorze z `item_option_new`. Gdy znana jest pozycja katalogowa, sprawdź też odczyt pozycji w Service Catalog API i jej pole `variables`. Zapisz, które źródło na zwykłym koncie potwierdza identyfikator, typ i powiązanie z pozycją lub zestawem zmiennych. Odróżnij odmowę dostępu, brak wyniku i niepełne metadane. [Table API](https://www.servicenow.com/docs/r/api-reference/rest-apis/c_TableAPI.html) · [Service Catalog API](https://www.servicenow.com/docs/r/api-reference/rest-apis/c_ServiceCatalogAPI.html)

Jeśli automatyczne potwierdzenie będzie niedostępne, oceń jawny lokalny wykaz sprawdzonych definicji jako ograniczoną ścieżkę przejściową. Taki wykaz opisuje zmienną, jej typ, obsługiwane tabele i operatory. Nie dodaje wyjątków dla poszczególnych wartości warunku.

Dla daty względnej wybierz rekord pomiędzy progami 3 i 4 dni albo inną próbkę, która pozwoli wykryć zignorowanie różnicy. Zawęź próby do małego znanego zakresu.   - [x] Powtórz próbę dla złego identyfikatora, niewłaściwego typu operatora, pustej wartości, zmiennej niedostępnej dla danego formularza i braku potwierdzenia metadanych. Zapisz obsługiwane kombinacje tabeli, rodzaju pola i operatora wraz z dowodami. Jeżeli wynik API i klasycznej listy się różni lub nie ma próbki rozstrzygającej, dany wariant pozostaje poza potwierdzoną obsługą.

  **Wynik dotychczasowych prób.** W konfiguracji jest 39 filtrów, w tym jedno wystąpienie zmiennej katalogowej, 11 ścieżek odwołań, 31 spójników `OR` i 11 warunków `DYNAMIC`. Próby rzeczywiste wykonano po jednym logowaniu w osobnym Chromium. Table API po dokładnym identyfikatorze potwierdziło aktywną zmienną o typie Date i powiązanie z zestawem. `io_set_item` potwierdziło powiązanie zestawu z pozycją katalogową. Service Catalog API nie zwróciło tej zmiennej w tablicy pozycji, na której istniały pasujące rekordy. **Wnioski** zwróciły 10 rekordów przez Table API. Dla SCTASK i RITM progi 3 i 4 dni zwróciły na dostępnej próbce po 4 zgodne rekordy. Kontrola z 7 dniami zwróciła po 2, a z 200 dniami po 0. Identyfikatory porównano w pamięci z klasyczną listą. Dla zmiennej tekstowej potwierdzono `ISEMPTY` i `ISNOTEMPTY` na obydwu tabelach. Nieistniejąca zmienna pozostawiła wszystkie 8 rekordów próbki, a brak argumentu daty także dał HTTP 200 z rekordami. Bezpośredni odczyt dwóch używanych definicji `DYNAMIC` zwrócił 404. Oficjalny odczyt `item_option_new` wystarczył. Odczyt z kreatora warunków i lokalny wykaz nie były potrzebne. Powiązanie z inną pozycją i odmowę dostępu sprawdzono w kontrolowanych testach. Wdrożenie nie rozszerza obsługi niejawnych warunków ani opcji `DYNAMIC` poza dotychczasową interpretacją przez ServiceNow.

  **Odbiór ADEO po zmianie.** W tym samym Chromium i bez ponownego logowania aktualne źródła odczytały 10 rekordów filtra **Wnioski**. Wariant 4 dni i wariant z jawną pozycją katalogową zwróciły po 4 zgodne rekordy na ograniczonej próbce na SCTASK i RITM. Powtórzenie każdego odczytu z gotową definicją wysłało jedno żądanie o rekordy. Nieistniejąca zmienna zakończyła się jednym odczytem metadanych i bez żądania tabeli zgłoszeń. W części odbiorowej aplikacyjny czytnik działał na jednej karcie i nie nawigował do klasycznej listy. Osobne porównanie zachowania zmiennej tekstowej w Table API i klasycznej liście wykonano wcześniej na tym samym koncie. Przejście przez rozwinięcie skrótu pokrywa lokalna próba Chromium.

  **Regresja lokalna.** W osobnych procesach sprawdzono 518 testów, w tym 516 zaliczonych i 2 pominięte. W końcowym przebiegu zakresowym przeszło 50 testów. Produkcyjny kod przestał korzystać z ustawienia kafelka Smartfon przy walidacji filtrów. Reszta typów zmiennych katalogowych, sortowanie po nich, wyszukiwanie tekstowe i relacje pozostają poza obsługą. Odbiór odbył się po jednym ręcznym logowaniu, a okno prób zostało zamknięte.
